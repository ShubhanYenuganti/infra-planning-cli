## Press-readiness check

Representative API for the gate: **`cloud-run-admin-pp-cli`** (GCP).

Rationale: mvanhorn already shipped this CLI, so we have a known-good output
to validate our substrate against. If our generated cloud-run-admin doesn't
match the known-good shape (modulo our convention layer), the substrate has
a bug.

### Result: UNBLOCKED (2026-05-20)

**Original blocker:** `printing-press generate --spec 'https://run.googleapis.com/$discovery/rest?version=v2'`
failed with `validation: base_url is required`. GCP Discovery is not OpenAPI 3.0.

**Resolution:** [apis.guru](https://apis.guru/) publishes OpenAPI 3.0 specs for all four
GCP and AWS CLIs in v1. No custom converter is needed. All `--spec` flags now point
at apis.guru URLs.

| CLI | apis.guru spec URL | Format |
|---|---|---|
| `cloud-run-admin-pp-cli` | `https://api.apis.guru/v2/specs/googleapis.com/run/v2/openapi.json` | OpenAPI 3.0 — direct |
| `cloud-functions-pp-cli` | `https://api.apis.guru/v2/specs/googleapis.com/cloudfunctions/v2/openapi.json` | OpenAPI 3.0 — direct |
| `lambda-pp-cli` | `https://api.apis.guru/v2/specs/amazonaws.com/lambda/2015-03-31/openapi.json` | OpenAPI 3.0 — direct |
| `apprunner-pp-cli` | `https://api.apis.guru/v2/specs/amazonaws.com/apprunner/2020-05-15/openapi.json` | OpenAPI 3.0 — direct |

**Azure:** Not on apis.guru as OpenAPI 3.0. `azure.com:web-WebApps` (Azure Functions)

## Retro (preliminary — substrate ship, Phase 6 blocked)

### What worked

- Substrate-first approach: linter + golden tests existed before any CLI,
  so when Phase 6 hits a real gap there's no half-baked CLI sitting in
  `library/` violating conventions.
- Per-CLI Go module structure validated with the lint-conventions and
  tests/golden modules — both are independently-versioned Go modules in
  the monorepo, exactly the pattern future CLIs will follow.
- Migration to `old-infra-cli` worktree clean: 58 deleted files, no
  residual cmd/internal/tests dirs on main.
- 5 lint checks + 4 golden checks all green against test fixtures and
  mock binaries respectively. The pattern (Check interface + Registry()
  function) makes adding a new check ~30 LOC.

### What surprised us

- **mvanhorn's press has zero cloud-infra APIs in its catalog.** The
  embedded catalog is 11 SaaS APIs (Stripe, GitHub, Stytch, Sentry, etc.).
  cloud-run-admin in the printing-press-library is a manual one-off, not
  representative of how press handles GCP/AWS/Azure broadly.
- **Press only consumes OpenAPI 3.0.** Doesn't natively parse GCP
  Discovery docs, AWS Smithy, or Azure ARM specs. This means every
  cloud-infra sprint will need a per-cloud spec-format adapter step
  before the press itself runs. Not captured in the design spec; needs
  to be added before v1.1.
- **Go 1.26 brew install was painless.** Spec called this the highest-risk
  open question; took ~30 seconds via `brew install go@1.26`. The risk
  evaporated.

### What we'd change for v1.1

- **Add a "spec resolution" step to the 8-step pipeline** that explicitly
  converts cloud-native spec formats (Discovery / Smithy / ARM) to
  OpenAPI 3.0 before invoking press. This becomes a per-cloud subtool
  (e.g., `tools/discovery-to-openapi/`).
- **Reconsider the press dependency.** If 100% of cloud APIs need a
  pre-conversion step, the press's "absorb gate" and "ecosystem absorb"
  phases (its key differentiators) may be wasted effort for cloud-infra.
  Either: (a) accept that cost for the SQLite/FTS5/conventions output;
  or (b) write a smaller cloud-specific generator that emits the same
  output shape without the press's SaaS-API assumptions.
- **The convention linter is currently text-based** (`strings.Contains`).
  Fine for v1 but a future CLI with creative formatting could pass the
  lint while violating spirit. Consider Go AST-based checks in v1.5+.

### Open questions to resolve before Phase 6 retry

1. Which spec format adapter for Cloud Run? (See "Press-readiness check"
   section above — 4 options.)
2. Does the same blocker apply to AWS (Smithy) and Azure (ARM)? Almost
   certainly yes; investigate before committing v1.1 sprint plan.
3. Should we vendor mvanhorn's printing-press-library `cloud-run-admin`
   output directly as a starting point (rather than re-generating from
   spec), accepting we lose press version pinning for that one CLI?
   This trades regen-readiness for shipping speed on the proof CLI.
