# Infra Press — Design Spec

**Date:** 2026-05-20
**Status:** Approved (brainstorming → spec)
**Project rename:** `infra-planning-cli` → `infra-press`

---

## 1. Summary

A curated library of focused, agent-native CLIs for cloud-infra APIs, generated by [mvanhorn's printing-press](https://github.com/mvanhorn/cli-printing-press), packaged with a hub (`AGENTS.md`, `catalog.yaml`, conventions doc, golden tests, install scripts) so any agent or skill — `/superpowers:brainstorming`, Claude Code, Cursor, a custom MCP — can discover and use them as primitives.

The project ships **tools**, not a workflow. The workflow is whatever the user (or their agent) brings.

**v1 scope:** 6 CLIs covering serverless + managed containers across AWS, GCP, Azure. Stateless services and scheduled jobs end-to-end. Vendor CLIs (`aws`, `gcloud`, `az`) cover everything else, with future sprints expanding coverage toward ~75 CLIs.

This spec replaces the entirety of the previous `infra-planning-cli` codebase, which moves to a `old-infra-cli` worktree for reference.

---

## 2. Locked decisions

| Decision | Choice |
|---|---|
| Approach | **D** — curated library + hub. No router binary, no NL-loop, no execution layer. |
| Generator | mvanhorn's printing-press (consumed as-is) |
| Library mechanics | **Approach 4 — Frozen Fork + Regen-Ready.** Commit press output directly. Edits are direct. Per-CLI `pressfile.yaml` manifest + `patches/` directory provide the substrate for a future update agent. |
| Update agent | **Out of scope for v1.** Separate future project. Library leaves the right shape for it. |
| v1 paradigm coverage | Serverless + Managed Containers (most self-contained compute paradigms) |
| v1 cloud coverage | AWS + GCP + Azure |
| v1 CLI count | 6 (2 paradigms × 3 clouds) |
| Sprint cadence | v1 substrate sprint (2-3 weeks), then ~1 sprint per 1-2 weeks adding ~3 CLIs |
| Distribution | macOS + Linux binaries. `install.sh` bulk path + `go install` per-CLI. No Windows, no brew in v1. |
| Versioning | Per-CLI SemVer. No root version. `catalog.yaml` is the pin. |

## 3. The 6 v1 CLIs

|  | Serverless | Managed Container |
|---|---|---|
| **AWS** | `lambda-pp-cli` | `apprunner-pp-cli` |
| **GCP** | `cloud-functions-pp-cli` | `cloud-run-admin-pp-cli` ✅ (exists upstream, re-generated under our conventions) |
| **Azure** | `functions-pp-cli` | `container-apps-pp-cli` |

### Per-CLI summary

**`lambda-pp-cli`** — AWS Lambda
- API: `lambda.amazonaws.com` (SigV4)
- Resources: Functions, Versions, Aliases, Layers, EventSourceMappings, FunctionUrlConfigs, Permissions
- Daily commands: `functions list/get/create/update-code/delete/invoke`, `aliases create`, `layers publish`, `event-source-mappings create`, `function-urls create`
- Compound: `stale`, `cold-starts`, `unused-layers`, `permissions-audit`
- Quirk: needs an IAM exec role on first create. Gap patch: `--auto-role` creates+attaches `AWSLambdaBasicExecutionRole`.

**`cloud-functions-pp-cli`** — GCP Cloud Functions (Gen2)
- API: `cloudfunctions.googleapis.com` v2 (ADC / service account)
- Resources: Functions, Operations
- Daily commands: `functions list/get/deploy/delete/call`, `operations list/get`
- Compound: `stale`, `revision-bloat` (Gen2 is Cloud Run under the hood), `failed-deploys`
- Quirk: `deploy` from source silently invokes Cloud Build + Artifact Registry.

**`functions-pp-cli`** — Azure Functions
- API: `Microsoft.Web/sites` (Function Apps are a flavor of Site) (Azure AD)
- Resources: FunctionApps (Sites), Functions, Slots, AppSettings, HostKeys, DeploymentSlots
- Daily commands: `function-apps list/get/create/delete`, `functions list/get`, `app-settings get/set`, `slots swap`, `host-keys list`
- Compound: `stale`, `cost-by-plan`, `missing-app-insights`, `cold-start-risk`
- Quirk: **hard dep on a Storage Account.** Documented fallback in root `AGENTS.md`: `az storage account create ...`.

**`apprunner-pp-cli`** — AWS App Runner
- API: `apprunner.amazonaws.com` (SigV4)
- Resources: Services, AutoScalingConfigurations, Connections, ObservabilityConfigurations, VpcConnectors, CustomDomains
- Daily commands: `services list/get/create/update/delete/pause/resume`, `services start-deployment`, `services list-operations`, `auto-scaling-configurations create`, `custom-domains associate`
- Compound: `stale`, `paused-services`, `failed-deploys`, `overprovisioned`
- Quirk: GitHub-sourced services need a `Connection` (one-time OAuth). Image-sourced services don't.

**`cloud-run-admin-pp-cli`** — GCP Cloud Run (re-generated under our conventions; mvanhorn's published version is the reference for shape)
- API: `run.googleapis.com` v2 Admin API (ADC / service account)
- Resources: Services, Jobs, Executions, Tasks, Operations, Revisions, IAM helpers
- Daily commands: `services list/get/replace/delete`, `services set-iam-policy`, `jobs list/run`, `executions list/cancel`, `revisions list`, `sync`, `search`, `sql`
- Compound: already implemented upstream (`stale`, etc.) — our regen reproduces them.

**`container-apps-pp-cli`** — Azure Container Apps
- API: `Microsoft.App` RP (Azure AD)
- Resources: ContainerApps, ManagedEnvironments, Jobs, Revisions, Replicas, DaprComponents
- Daily commands: `apps list/get/create/update/delete`, `environments list/create`, `revisions list/activate/deactivate/restart`, `replicas list/exec`, `jobs list/start/stop`
- Compound: `stale`, `revision-bloat`, `idle`, `env-utilization`
- Quirk: every app needs a parent **Managed Environment**. Gap patch: `apps create --auto-environment` creates the env on-the-fly if none exists.

## 4. Capability profile

**Service shapes deployable with v1:**
- Public HTTPS APIs (REST, GraphQL, JSON-RPC, MCP HTTP servers)
- Webhook receivers
- Scheduled jobs (Cloud Run Jobs, Container Apps Jobs, Lambda + EventBridge cron)
- Event-driven processors (function row binds to event sources)
- AI agent backends (LLM proxies, RAG endpoints)
- Bots (Discord/Slack/Telegram)
- BFFs / API gateways
- Image/file transform pipelines

**Cross-cloud compound queries (the SQLite-layer unlock):**
- `stale --all` across the 6 stores
- Total managed-compute footprint
- Service-name search across clouds
- Public-endpoints-without-auth security audit
- Cold-start risk audit
- Tag/label hygiene
- Multi-cloud canary readiness
- Idle-compute spend triangulation

**Out of v1 (needs vendor CLI fallback):**
- Stateful services (DB) — v2.0/v2.1
- Object storage — v1.2
- Private networking — v1.3
- Custom container images — v1.5 (registries)
- Secrets — v1.6
- Custom domains end-to-end (DNS) — v2.2
- Event sources for non-function compute — v1.8
- Kubernetes workloads — v1.7

## 7. Hub artifacts (detail)

### `AGENTS.md` (root) — load-bearing

The first thing any agent reads. Sections:
- One-paragraph project description (stateless services + scheduled jobs across clouds)
- "When to reach for what" table (need → CLI → cloud)
- Conventions every CLI follows (auto-JSON, exit codes, `sync`/`search`/`sql`, `~/.infra-press/<cli>.db`, `--data-source`, `--dry-run`, `--select`)
- Auth resolution order per cloud
- Known fallbacks to vendor CLIs (Azure Functions storage account, Lambda IAM role)
- Pointer to `docs/compound-recipes.md`

Grows by row-addition each sprint. No structural changes needed at scale.

### `catalog.yaml` — machine-readable

```yaml
version: 1
clis:
  - name: lambda-pp-cli
    cloud: aws
    service: lambda
    paradigm: serverless
    path: library/aws/lambda
    binary: lambda-pp-cli
    install: github.com/ShubhanYenuganti/infra-press/library/aws/lambda
    status: stable          # bootstrapping | preview | stable
    press_version: v1.4.2
    spec_version: 2024-11-01
    daily_commands: [functions list, functions create, functions invoke]
    compound_commands: [stale, cold-starts, unused-layers, permissions-audit]
    known_gaps:
      - "First use requires IAM exec role; use --auto-role"
```

Consumed by: future update agent, `tools/lint-conventions`, install script, any agent doing programmatic discovery.

### `README.md` — human pitch

Standard project README — what/why/quick install/CLI table/roadmap link/contributing link. Not load-bearing for agents.

### `docs/conventions.md` — linter source of truth

Sections:
- Flag names & semantics (exhaustive list: `--json`, `--compact`, `--select`, `--dry-run`, `--data-source`, `--yes`, `--idempotent`, `--ignore-missing`, `--stdin`, `--human-friendly`)
- Exit code table (0 ok / 2 user err / 3 auth / 4 not found / 5 conflict / 7 rate-limit)
- SQLite path & schema basics
- `sync`/`search`/`sql` subcommand contracts
- Auth resolution order per cloud
- Output shape (auto-JSON when piped, `--compact`, `--select`)
- `--dry-run` semantics
- Regen contract (what's preserved, what's overwritten)
- Patch directory rules

### `docs/compound-recipes.md` — cross-CLI joins

SQL snippets + one-line descriptions that join across the 6 SQLite stores. Examples: stale services across clouds, public endpoints without auth, idle-compute spend triangulation. Grows as sprints add stores.

## 8. Per-CLI build workflow (8-step pipeline)

Applied to every CLI in every sprint.

```
1. press-readiness check  (once per sprint, against representative API)
2. spec resolve
3. press generate
4. scorecard
5. patch gaps + compound commands
6. lint (conventions)
7. golden tests
8. tag + release
```

### Step 1 — Press-readiness check (sprint gate)

Smoke-test the press against one representative API. Verify:
- Press can parse the spec format
- Press handles the cloud's auth model
- Generated binary authenticates and lists a resource end-to-end

If fails → sprint blocked on press extensions. Don't bulk-generate broken CLIs.

### Step 2 — Spec resolve

Per CLI: identify canonical spec URL, record `spec_url`/`spec_version`/`spec_etag` in stub `pressfile.yaml`, verify spec fetchable.

### Step 3 — Press generate

```
printing-press generate \
  --spec <url> \
  --output library/<cloud>/<service>/ \
  --pressfile library/<cloud>/<service>/pressfile.yaml
```

### Step 4 — Scorecard

Standardized assessment. Each CLI gets graded:

| Check | Pass criteria |
|---|---|
| Binary builds | `go build ./cmd/...` succeeds |
| Help works | `<cli> --help` lists resources |
| Auth works | `<cli> services list` returns 200 |
| Auto-JSON when piped | `<cli> services list \| cat` outputs JSON |
| Exit codes correct | Invalid args → 2; no creds → 3; bad resource → 4 |
| `sync` present | `<cli> sync --dry-run` runs |
| `search` present | `<cli> search --help` exists |
| `sql` present | `<cli> sql --help` exists |
| SQLite path correct | sync writes to `~/.infra-press/<cli>.db` |
| `--data-source` flag | Live/local/auto modes work |
| AGENTS.md non-trivial | >500 words, lists resources |

Output: `library/<cloud>/<service>/scorecard.md` (one-time onboarding artifact).

**Decision after scorecard:**
- All ✅ → proceed
- Convention ❌ across CLIs → patch press, re-run for whole sprint
- CLI-specific ❌ → record as gap-patch candidate, proceed

### Step 5 — Patch gaps + add compound commands

Three categories in `patches/`:

1. **Gap patches** — fixes for press output (e.g., `--auto-role`, storage-account bootstrap, `--auto-environment`)
2. **Compound commands** — added subcommands not auto-generated
3. **`AGENTS.append.md`** — anything the agent should know

Every patch file gets a row in `pressfile.yaml`'s `patches[]` with `reason`.

### Step 6 — Lint (conventions)

`tools/lint-conventions` runs the durable checks. Same content as scorecard but applied to *final* code (post-patches). CI gate.

### Step 7 — Golden tests

Cross-library black-box conformance via `tests/golden/`. See Section 10.

### Step 8 — Tag + release

- Bump version in `library/<cloud>/<service>/`
- Update `catalog.yaml`
- Update root `AGENTS.md` if status changed
- GitHub release tagged `<cli>/vX.Y.Z` with built binary

## 9. Convention enforcement — `tools/lint-conventions/`

Small Go program (~500 LOC). Reads `library/<cloud>/<service>/` and checks compliance with `docs/conventions.md`. Run modes:

```bash
go run ./tools/lint-conventions library/                     # lint everything
go run ./tools/lint-conventions library/aws/lambda           # lint one
go run ./tools/lint-conventions --ci library/                # CI mode (exit non-zero on violations)
```

Checks:
- Exit code table compliance (greps for patterns)
- Subcommand presence (`sync`, `search`, `sql`)
- Flag presence (`--json`, `--dry-run`, `--select`, `--data-source`, `--compact`)
- SQLite path string matches `~/.infra-press/<cli>.db`
- `pressfile.yaml` schema valid
- Required hub artifacts present (`AGENTS.md`, `README.md`)

**Load-bearing for keeping 6 → 75 CLIs uniform.** New conventions added at sprint boundaries only (so existing CLIs aren't broken mid-sprint).

## 10. Tests & CI

### Two test layers

**Layer 1 — Per-CLI tests** (`library/<cloud>/<service>/tests/`)
- `generated/` — press-emitted, replaced on regen
- `patches/` — human-authored, test patch behavior

**Layer 2 — Golden tests** (`tests/golden/`)
- Orchestrator iterates over `catalog.yaml`, runs each check on each CLI
- Black-box conformance: same checks as the convention linter, but against running binaries

```
tests/golden/
├── golden_test.go            ← orchestrator
├── checks/
│   ├── help_exits_zero.go
│   ├── version_is_semver.go
│   ├── sync_dry_run_outputs_json.go
│   ├── unknown_command_exits_2.go
│   ├── unknown_resource_exits_4.go
│   ├── auto_json_when_piped.go
│   ├── compact_flag_reduces_fields.go
│   ├── data_source_modes.go
│   └── sqlite_path_correct.go
└── fixtures/
    └── mock-creds.yaml
```

### Mock layer

**v1 approach:** golden tests run only auth-resolution path + exit codes + help-text. Skip anything needing real API calls. (Option 2 from brainstorming.)

**Future:** request mock-mode flag from press upstream (records/replays API responses).

### CI workflows (`.github/workflows/`)

```
lint.yml          ← every PR. Runs tools/lint-conventions.
per-cli-tests.yml ← every PR. Matrix over changed CLIs (paths filter).
golden.yml        ← every PR. Full Layer 2 sweep.
release.yml       ← tag push (<cli>/vX.Y.Z). Builds binary, runs lint + tests, publishes release.
nightly.yml       ← nightly. Full build of all CLIs, smoke tests, reports failures to issue.
```

### Scale projection

| Stage | CLIs | Layer 1 (est.) | Layer 2 | Total | CI time |
|---|---|---|---|---|---|
| v1 | 6 | ~120 | 54 | 174 | ~2 min |
| v1.4 | 18 | ~360 | 162 | 522 | ~4 min |
| v2.0 | 50 | ~1000 | 450 | 1450 | ~10 min |
| v2.4 | 75 | ~1500 | 675 | 2175 | ~15 min |

### Out of CI for v1

- Live API smoke tests (cost + cred management — manual `scripts/smoke-<cli>.sh`)
- Regen automation (future update agent)
- Spec-drift monitoring (future update agent)
- Cross-cloud integration tests (cost-prohibitive)

## 11. Distribution & install

### Three install paths

| Path | Audience | Command |
|---|---|---|
| **Bulk** | "Give me everything" | `curl ... \| sh` (runs `scripts/install.sh`) |
| **Per-CLI** | "I only want lambda" | `go install github.com/ShubhanYenuganti/infra-press/library/aws/lambda/cmd/lambda-pp-cli@latest` |
| **Direct binary** | Reproducible/CI | `curl -L <release-url> -o ...` |

### `scripts/install.sh`

Reads `catalog.yaml` from `main`. For each `status: stable` CLI: detect platform → fetch release binary → drop in `${INFRA_PRESS_HOME:-$HOME/.infra-press}/bin/`. Idempotent (re-running upgrades to current pinned versions).

### Auth doctor scripts

Per cloud: `doctor-aws.sh`, `doctor-gcp.sh`, `doctor-azure.sh`. Run auth-resolution checks without calling any API. Surfaces "is your SDK chain set up, what identity is active, can you reach the metadata service." Root `AGENTS.md` directs agents to run the relevant doctor first.

### Binary distribution

Per CLI, per release: `darwin-amd64`, `darwin-arm64`, `linux-amd64`, `linux-arm64`. Built by `release.yml` on tag push.

### Update flow

- **v1:** manual. User re-runs `install.sh`. Catalog on `main` is the pin.
- **Future:** update agent regenerates outdated CLIs, opens PR, CI passes, merge, release, users re-run install.

### Versioning

Per-CLI SemVer (`lambda-pp-cli/v0.1.0`). No root repo version. `catalog.yaml` is the snapshot pin.

## 12. Sprint workflow

Every sprint follows the same 6-phase template, recorded at `docs/sprints/v1.X-<domain>.md`.

### Sprint phases

```
Phase 1: Plan         (~half day)
Phase 2: Ready check  (~1 day)   ← sprint gate; STOP if fails
Phase 3: Bulk generate(~1 day)
Phase 4: Patch + integrate (~3-5 days, parallel per CLI)
Phase 5: Cross-cloud finishing (~1 day)
Phase 6: Release      (~half day)
```

Per-sprint total: ~1 week sustained.

### Sprint planning doc template

Each sprint doc has:
- Goal (one sentence)
- CLIs in this sprint (table)
- Press-readiness check (representative API)
- Per-CLI gap notes
- Cross-cloud guidance to add to root `AGENTS.md`
- Definition of done (checklist)
- Retro (filled at end)

### v1 is the substrate sprint

v1 ships 6 CLIs AND builds the regen-ready substrate. v1's Phase 1 has extra one-time deliverables:

- [ ] Repo rename `infra-planning-cli` → `infra-press`
- [ ] Old code moved to `old-infra-cli` worktree
- [ ] `docs/conventions.md` written
- [ ] `tools/lint-conventions/` implemented
- [ ] `tests/golden/` orchestrator + 9 initial checks implemented
- [ ] `scripts/install.sh`, `scripts/doctor-{aws,gcp,azure}.sh` implemented
- [ ] Root `AGENTS.md` authored
- [ ] `catalog.yaml` v1 schema defined
- [ ] CI workflows (`lint.yml`, `per-cli-tests.yml`, `golden.yml`, `release.yml`, `nightly.yml`)
- [ ] `pressfile.yaml` schema documented
- [ ] Patch convention documented

### Suggested v1 build order

1. `cloud-run-admin-pp-cli` (integrate existing, validate substrate against known-good output)
2. `apprunner-pp-cli` (validates AWS sigv4 path)
3. `lambda-pp-cli` (second AWS, parallel work)
4. `container-apps-pp-cli` (validates Azure AD path)
5. `functions-pp-cli` (validates storage-account-dep flow)
6. `cloud-functions-pp-cli` (last, lowest risk)

### v1 estimate

2-3 weeks for substrate + 6 CLIs. Future sprints reuse all substrate, run ~1 week each.

### Sprint cadence going forward

| Mode | Pattern |
|---|---|
| Active development | 1 sprint / 1-2 weeks. ~3 CLIs per sprint. |
| Maintenance mode | 1 sprint / month. Backlog-driven. |
| Press regen pulse | Whenever future update agent fires. Not a sprint — automated. |

### Sprint backlog

```

v1.1       IAM
v1.2       Object storage
v1.3       Networking foundations
v1.4       VMs
v1.5       Container registries
v1.6       Secrets
v1.7       Kubernetes

v2.1       Databases — NoSQL

v2.3       CI/CD

```

Order is mutable between sprints based on real usage signals. Lock decision at each sprint's Phase 1.

### Cross-sprint concerns

- Root `AGENTS.md` grows by row-addition + cross-cloud guidance callouts
- `docs/compound-recipes.md` grows as more stores enable richer joins
- Sprint retros feed the next sprint's plan
- `tools/lint-conventions/` evolves slowly; new checks land at sprint boundaries only
- Future update agent watches every shipped CLI

### Sprint failure modes

| Failure | Trigger | Mitigation |
|---|---|---|
| Press can't handle cloud auth | Phase 2 ready-check fails | Patch press OR pick different sprint OR hand-write auth shim |
| Press output uniformly bad | Phase 3 reveals systemic gap | Patch press once, re-run for whole sprint |
| One CLI has wildly different shape | API doesn't fit press model | Defer that CLI OR hand-author more in `patches/`. Ship sprint with N-1 CLIs |
| Cross-cloud guidance wrong post-ship | User reports it | Patch `AGENTS.md` + `AGENTS.append.md`. Not a sprint blocker |

## 15. Open questions (flag during implementation, not spec blockers)

1. **mvanhorn's press requires Go 1.26.3+.** Previous attempt at compliance was blocked by Go 1.20 availability. Resolve before v1 Phase 2 (ready-check). If unresolvable, project stalls — highest-risk dependency.

2. **mvanhorn's press relies on Claude Code for the curated agent loop.** Binary works standalone but polish loop runs through Claude Code's `/printing-press` slash command. Decide: run press as-is via Claude Code, or invoke binary directly and skip curated loop. Affects Phase 3 (bulk generate).

3. **Spec sources for each v1 CLI need verification.** AWS Lambda and Cloud Run have clean spec URLs. Azure Functions (= a sub-shape of Microsoft.Web ARM) may require slicing a larger spec. Verify per-CLI in Phase 2.

4. **Naming collision:** mvanhorn's `cloud-run-admin-pp-cli` already exists in their library. Decision locked: **re-generate from spec ourselves** (don't depend on their release cadence). Keeps everything uniform under our conventions.

5. **`CLAUDE.md` "NEVER `git push`" policy + release pipeline.** All releases tag-driven from manual `git push --tags`. Confirmed clean: no CI workflow ever pushes commits back to main; `release.yml` only publishes binaries.
